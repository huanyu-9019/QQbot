# QQ Evolution Supervisor

This directory contains the control-plane primitives for the unattended QQ bot improvement loop.

The supervisor is intentionally single-job on the 1 GiB Codex host. Production credentials, raw audit records, memory files, snapshots, and model transcripts stay outside Git. The model may return findings and a unified diff only; fixed code controls paths, tests, service names, restart, health checks, observation, and rollback.

Before enabling the systemd unit, configure the server-local `codex-relay`, SSH key, production source path, and state directories with mode `0700`/`0600`. Run the Python test suite and a simulated rollback cycle first.

The evaluator reads its source tree from `/home/admin/qq-evolution/development` by default. Set `QQ_EVOLUTION_REPO` in the server-local service environment to use another development checkout; the model working directory and patch allowlist are derived from the same path.

The service polls every five minutes and evaluates at most once per thirty minutes. Windows containing at least three reply pairs receive qualitative model assessment even when delivery succeeded. A hash of the last completed audit window prevents repeatedly changing the bot against unchanged conversations. Model request failures remain retryable errors.

Candidates have their hunk counts recomputed, then pass strict path and structure validation and a Git application check. Production snapshots its source, applies the same Git patch format, runs the Node suite, restarts the bridge, and checks service health over sixty seconds; failures restore the snapshot. Healthy releases advance the development Git baseline. With `QQ_EVOLUTION_GIT_REMOTE=origin`, commits are automatically pushed to `codex/qq-autonomous-evolution`; pending pushes retry on later polls. Two consecutive failed releases trigger a six-hour backoff before automatic recovery.

This loop learns by updating the bot's checked-in persona, rules and source. It does not train new model weights. Passing tests and service health checks do not establish that every conversational change improves quality; continued audit assessment supplies later feedback.

The production bridge maintains a private 14-day, per-group aggregate style profile from incoming messages. It stores salted group hashes and numeric cadence/tone counters only, activates after 30 messages, and never retains member names or example phrases in this profile. Conversation audit schema v2 also records explicit terminal outcomes for intentional silence and delivery failures without duplicating message text. Legacy v1 audit rows remain valid learning evidence but are excluded from live unanswered-turn alarms because they cannot distinguish a group decision from a missed reply.

`qq-status-report.timer` on the control host runs `status_report.py` to publish one combined QQ Space health report for both machines. Its private `report-schedule.json` stores the original start epoch and last confirmed slot: five-minute slots for two hours, then four-hour slots. Reboots preserve that phase. The report includes both hosts' resources, supervisor heartbeat/recent audit-fetch status, and production bridge/API status; SSH or publication failure fails the job instead of inventing a successful report. The old production `qq-space-disk-report.timer` is disabled. All QZone publications share an OS flock and run as `hermes`, including manual root invocations, to keep state ownership and duplicate prevention consistent.

Health reporting checks the cached provider route state, service state and recent v2 conversation outcomes; it distinguishes a usable fallback chain from proven end-to-end QQ reply health. The bridge's final fallback uses the server-local `DEEPSEEK_API_KEY` with the verified `deepseek-flash` model after Hermes errors, empty results, or a 30-second timeout. This backup is text-only and has no tools; it must not claim to have searched or interpreted pictures. SSH probes/publication retry connection failures, the timer checks due slots every minute, and systemd retries failed jobs after twenty seconds; these checks preserve the requested publication cadence and original two-hour transition.

`qq-incident.timer` independently probes API, bridge, cached provider availability, and overdue failed or unanswered v2 turns every minute, outside the 30-minute conversational assessment cooldown. An available fallback with Gemini down is a healthy degraded route, not an incident. True incidents trigger server `codex-relay` diagnosis with `incident.schema.json`; Codex can request fixed, backed-up provider failover, API/bridge restart, or a source patch through the existing rollback gate. Every action is followed by fresh probes; incomplete recovery stays degraded and retries. Repair and quality release share `job.lock` to prevent overlap on the 1 GiB host. If the Codex request fails, a fixed continuity repair is labeled separately. SSH failure remains unhealthy. Intentional silence is not treated as a missed reply.

The production `qq-chat-router.service` owns provider order and keys in root-controlled SSH-pushed config plus a hermes-owned mode-0600 runtime copy. Chat requests hit only loopback port 8650. Provider failures are cached immediately, subsequent messages start at the first cached-healthy provider, and recovery probes run in the background every five minutes; successful recovery restores priority order. The order is Gemini, Grok, relay DeepSeek, then official DeepSeek; active-provider changes publish to QQ Space. The bridge resolves provider availability on every request from cached router state, without issuing a health request to Gemini. The control-host incident probe reads the router's cached health state, avoiding duplicate external model probes.

`supervisor.py` runs one explicit naturalness iteration every 30 minutes regardless of whether a code patch is justified. Each iteration reviews anonymized context for language naturalness, social context, emotion, humor, memory behavior, persona stability and turn-taking. It reads the previous reflection and appends each new reflection to a private mode-0600 JSONL growth archive. Findings select an appropriate persona, memory, rule, tool or code layer; changes still require allowlist validation, full tests, production snapshot, rollback and health gates. No-change rounds preserve a concrete lesson rather than making a cosmetic code edit. The loop improves prompts, rules, memory behavior and code; it does not update model weights.
